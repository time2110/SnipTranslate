# SnipTranslate 技术难点与兼容性问题复盘

## 1. 文档目的

本文档记录 SnipTranslate 开发过程中已经遇到的主要技术难点、Windows 兼容性问题、根本原因、当前解决方案和后续改进建议。它既是项目复盘，也可作为排查手册。

文档基线：

- 代码提交：`c958f52`
- 安装包版本：`0.3.0`
- 桌面框架：WPF / .NET 10 / Windows x64
- OCR：RapidOCRLib + PP-OCRv5 ONNX
- 安装包：Inno Setup

## 2. 整体架构取舍

SnipTranslate 的核心目标是“截图后就地完成标注、OCR 和翻译”，因此采用了两进程架构：

```text
SnipTranslate.exe（WPF 主程序）
  ├─ 全屏截图与选区
  ├─ 标注、放大镜、贴图
  ├─ OCR/翻译结果卡片
  ├─ 设置、托盘和全局快捷键
  └─ Named Pipe
       └─ SnipTranslate.OcrWorker.exe
            ├─ RapidOCR / ONNX Runtime
            ├─ Mobile / Server 模型
            └─ 文本行和段落重排
```

将 OCR 拆成独立 Worker 的原因：

- ONNX、OpenCV 和 OCR 模型会显著增加内存占用。
- OCR 初始化或原生库异常不应拖垮截图主程序。
- Worker 空闲 10 分钟后自动退出，可回收 Session 和模型内存。

代价是需要处理进程启动、命名管道、请求取消、临时图片和协议版本兼容。

## 3. 截图、DPI 与多显示器

### 3.1 现象

- 某些电脑显示“无法截取屏幕”。
- 高 DPI 显示器上，选区、鼠标位置与真实像素不一致。
- 不同缩放比例的多显示器组合中，截图窗口可能偏移或尺寸错误。

### 3.2 原因

WPF 主要使用 DIP（设备无关单位），GDI `BitBlt` 使用物理像素。在 125%、150% 或混合 DPI 显示器上，如果混用两套坐标系，就会出现位置和大小偏差。

截图还可能因为 GDI 句柄创建失败、`BitBlt` 返回失败、显卡驱动或特殊桌面会话而失败。

### 3.3 解决方案

- 应用 Manifest 声明 `PerMonitorV2` DPI Awareness。
- 对每个显示器分别获取物理边界并截图。
- 通过 `SetWindowPos` 将遮罩窗口放到对应的屏幕物理区域。
- 渲染文字时使用 `VisualTreeHelper.GetDpi(...).PixelsPerDip`。
- 对 GDI 对象、HBITMAP 和 DC 做成对释放，避免长时间运行后句柄泄漏。
- 截图失败时记录具体阶段，而不是只显示统一错误。

### 3.4 仍需注意

- DRM 视频、某些硬件叠加层或受保护内容可能截取为黑屏，这不是普通 GDI 截图可完全解决的问题。
- 远程桌面、切换用户或显卡驱动重启期间仍可能失败。

## 4. 鼠标坐标、文字输入与输入法

### 4.1 文字输入位置偏低

#### 原因

用户点击的是 I-beam 光标热点，但 WPF 文字绘制原点更接近文字外接矩形左上角。直接把点击 Y 坐标当作文字顶部，视觉上就会偏低。

#### 解决方案

- 根据字号对 Y 坐标做基线补偿，当前为约 `fontSize * 0.58`。
- 文字原点限制在当前选区内。
- 真正的 `TextBox` 缩小到几乎不可见，只负责 IME、光标和组字；文字由截图画布实时渲染。
- `Ctrl+Enter` 提交文字，失去焦点时也提交。

### 4.2 中文输入法下按 C 无法复制颜色

#### 原因

IME 在组字状态下会优先消费字符输入事件。如果快捷键依赖“输入字符 C”而不是物理键事件，就会被输入法截获。

#### 解决方案

- 在窗口 `PreviewKeyDown` 阶段识别 `Key.System` 和实际键值。
- 颜色复制直接处理按键，不等待文字输入事件。
- `Shift` 切换 HEX/RGB，`C` 复制当前放大镜正在显示的格式。
- 进入文字标注状态时，快捷键逻辑让位给文本编辑器。

## 5. 放大镜、工具条和结果卡片的层级问题

### 5.1 现象

- 放大镜被工具条盖住。
- 鼠标移到 OCR 结果卡片时，放大镜仍然跟随。
- 鼠标移入卡片后仍保持十字或绘图光标。
- 选中画笔、矩形、箭头后，额外的鼠标提示影响视野。

### 5.2 原因

放大镜最初由截图画布自身渲染，而工具条和结果卡片位于更高的 WPF 视觉层。同时，全窗口的鼠标事件会继续更新放大镜，即使鼠标已经离开截图画布。

### 5.3 解决方案

- 使用 `Adorner` 单独渲染指针叠加层，使其可位于主画布之上。
- 放大镜只在鼠标命中截图画布时显示。
- 工具条、结果卡片和编辑控件显式使用普通箭头光标。
- 标注工具仅改变实际光标形状，取消鼠标下方的文字提示。
- 放大镜会根据画布边界和工具条位置自动翻转显示方向。

## 6. 窗口和控件智能吸附

### 6.1 难点

仅使用 `EnumWindows` 只能拿到顶层窗口，无法识别按钮、输入框、图片等内部控件。如果在鼠标移动事件中同步遍历 UI Automation 树，又会导致截图界面卡顿。

### 6.2 解决方案

- 开始截图前先快照所有可见顶层窗口。
- 过滤隐藏窗口、最小化窗口、桌面/Shell 窗口和截图程序自身。
- 当鼠标首次进入某个窗口时，在后台线程中通过 UI Automation 查询子控件。
- 对控件矩形做缓存、去重、面积排序和边界过滤，避免每次鼠标移动都遍历自动化树。
- 滚轮在“控件 → 窗口 → 整个屏幕”之间切换。
- 按住 `Alt` 时临时关闭吸附，可直接自由框选。

### 6.3 兼容边界

- 管理员权限的程序可能不向普通权限进程暴露完整 UI Automation 信息。
- 游戏、自绘界面、DirectX 窗口、某些 Chromium 内容或定制控件可能只暴露窗口级边界。
- UI Automation 查询可能超时或抛出 COM 异常；当前会安全回退到窗口吸附。

## 7. OCR 集成和模型兼容

### 7.1 模型不是只有一个文件

RapidOCR 完整链路包含：

1. 文本检测模型（det）。
2. 文本方向分类模型（cls）。
3. 文字识别模型（rec）。
4. 与 rec 模型完全匹配的字典。

只替换 rec 而不替换字典，会出现字符索引错位、乱码或数组越界。模型版本、字典和 RapidOCRLib 的输入尺寸规则也必须匹配。

### 7.2 当前模型策略

- 自动/中英日：PP-OCRv5 Mobile 通用识别模型。
- English 优先：PP-OCRv5 English Mobile rec + English 字典。
- 韩文：PP-OCRv5 Korean Mobile rec + Korean 字典。
- 准确模式：PP-OCRv5 Server det + Server 通用 rec。

RapidOCR 模型清单中没有独立的 English Server rec，因此“英文准确模式”使用支持英文的通用 PP-OCRv5 Server rec，不伪造不存在的模型名称。

### 7.3 模型下载与校验

曾经的风险是下载链接变化、下载中断、HTML 错误页被当作 ONNX 文件，或用户本地模型版本不一致。

解决方案：

- 下载脚本为每个模型固定来源 URL 和 SHA-256。
- 已存在文件必须校验通过才会跳过下载。
- 下载后再次校验，不匹配立即终止打包。
- 安装包必须包含 Worker 依赖、ONNX 模型和字典。

### 7.4 英文小字识别差

#### 原因

- 自动模式原本只跑中英日通用模型，没有调用英文专用 rec 复核。
- 小字、细字体、低对比度、压缩噪点和复杂背景会同时降低 det 和 rec 的质量。
- Mobile 模型优先速度和体积，复杂场景的容错率低于 Server 模型。

#### 解决方案

- English 识别前根据图像尺寸放大 1.25–3 倍。
- 转换灰度并提高对比度，改善细字笔与背景的区分。
- 增强模式降低文本框阈值、增加 padding 和最大检测尺寸。
- 自动语言模式会另外执行英文专用模型，根据字符置信度、可读字符比例和拉丁字符比例择优。
- 设置页可在 Mobile 快速和 Server 准确模式之间切换。

### 7.5 第一次识别错误无法重试

原结果卡片只有“重新翻译”，但翻译只处理现有 OCR 文本，无法修复 OCR 错误。

当前方案：

- 结果卡片内新增“重新识别”。
- `Ctrl+R` 可在不重新框选的情况下对原选区增强重试。
- 如果已经显示翻译，OCR 更新后自动刷新译文。
- 重新识别失败时恢复上一次原文和译文，保证内容仍可复制。

### 7.6 OCR 文本块顺序错乱

OCR 引擎返回的是文本框列表，不是自然段落。直接拼接会造成行顺序错乱、英文单词粘连或多栏内容交叉。

当前方案使用文本框的上下重叠、中心 Y、左边界、行高和段落间距重建行与段落，并在相邻拉丁字符框之间按几何间隔补空格。

## 8. OCR 性能、内存和取消

### 8.1 问题来源

- Mobile det/rec/cls、English/Korean rec 和 Server det/rec 同时存在时，模型文件和 ONNX Session 占用明显增加。
- Server det 和 Server rec 合计约 164.7 MB，还不包含 ONNX Runtime 运行时内存。
- 自动英文复核需要两次推理，准确性提高的同时会增加延迟。

### 8.2 当前策略

- 默认使用 Mobile 快速模式。
- 按语言和精度延迟创建 OCR Session，创建后在 Worker 进程中复用。
- 新请求或关闭截图时取消已有请求。
- Worker 无连接 10 分钟后退出，由操作系统彻底回收原生内存。

### 8.3 后续建议

- 将 Server 模型做成安装器可选组件或首次使用时按需下载，可显著缩小默认安装包。
- 根据英文概率决定是否复核，避免纯中文图片也跑两次。
- 增加性能记录：模型初始化、det、cls、rec、布局重排和 IPC 分项耗时。

## 9. OCR 结果与翻译的界面集成

### 9.1 原问题

OCR 和翻译结果最初在另一个窗口中显示，用户必须在截图遮罩和结果窗口之间切换，破坏了快速操作流。

### 9.2 解决方案

- 将 OCR/翻译做成截图选区旁边的内嵌卡片。
- 优先放在选区右侧，空间不足放左侧，再不足则限制在当前屏幕内。
- OCR 完成后先显示原文，卡片顶部提供“翻译”，不重复跑 OCR。
- 译文标题和状态显示实际使用的翻译接口，不再写死为 Google。

## 10. Google 429、翻译失败与接口切换

### 10.1 为什么会出现 429

Google Web 方案是公开 Web 端点，不是有 SLA 的正式商业 API。它可能根据出口 IP、请求频率、文本量或反滥用策略返回 `429 Too Many Requests`。使用代理也不能保证不限流，共享代理节点反而可能更容易被限制。

### 10.2 当前解决方案

- 提供 Google Web、微软/Bing Translator、LibreTranslate、MyMemory 和自定义 HTTP API 适配器。
- 翻译接口可添加、编辑、停用、删除和拖动排序。
- 启用自动切换时，按列表顺序请求下一个可用接口。
- 429 后该接口冷却 1 分钟；401/403 冷却 5 分钟；其他连续失败达到阈值后冷却 30 秒。
- 缓存最近 128 个翻译结果，相同文本、语言和接口配置可直接命中缓存。
- Google 遇到 429 时尊重 `Retry-After`，但单次等待受限，避免卡住截图界面。
- 即使翻译失败，OCR 原文仍可复制。

### 10.3 代理兼容

支持跟随 Windows 系统代理、完全直连以及自定义 HTTP/HTTPS/SOCKS5 代理。代理用户名和密码由当前 Windows 用户的 DPAPI 加密后再写入设置文件。

需注意：系统代理和应用内代理的行为受 .NET `HttpClientHandler` 影响；证书拦截、企业网关和错误的 SOCKS 协议都可能造成 TLS 或连接错误。

## 11. 设置页的接口数量与编辑交互

### 11.1 原问题

“接口类型”下拉框有 5 种类型，左侧列表只有已添加的实例。用户容易把“类型数量”理解为“已配置接口数量”。早期界面又将顺序列表和编辑表单分成两个区域，缺少明确的单项保存动作。

### 11.2 解决方案

- 左侧明确表示“已添加的接口实例”，同类型允许添加多次。
- 右侧只编辑当前选中的实例。
- 增加“保存此接口”，再由“保存全部”持久化整个设置。
- 拖动左侧实例即改变失败后的调用顺序。
- “测试翻译”仅测试当前选中的接口，结果显示在设置窗口内。

## 12. Windows 剪贴板竞争

### 12.1 现象与原因

Windows 剪贴板是跨进程共享资源。输入法、剪贴板历史、远程桌面、即时通信软件或其他截图工具可能短暂占用它。WPF `Clipboard.SetText/SetImage` 在这种情况下会抛出 COM 异常。

### 12.2 解决方案

- 所有文本和图像写入统一经过 `ClipboardService`。
- 最多尝试 6 次，间隔按 20 ms 递增。
- 仅重试 COM 占用类异常，不吞掉其他编程错误。
- 最终失败时显示“剪贴板正被其他程序占用”，便于用户重试。

## 13. 全局快捷键兼容

### 13.1 难点

- `RegisterHotKey` 可能因快捷键被其他程序占用而失败。
- 按键名称、WPF `Key` 和 Win32 Virtual Key 不是同一个类型。
- 长按会反复触发。
- 截图和截图翻译不能使用同一组快捷键。

### 13.2 解决方案

- 设置页通过 `KeyInterop.VirtualKeyFromKey` 记录实际 Virtual Key。
- 支持 Ctrl/Alt/Shift/Win 组合，F1–F12 允许单独使用。
- 保存前检查两个功能是否重复。
- 注册时使用 `MOD_NOREPEAT`。
- 设置窗口关闭后重新注册，无需重启程序。

## 14. 托盘、开机自启动与安装器

### 14.1 托盘图标

WPF 本身没有系统托盘控件，项目需使用 Windows Forms NotifyIcon 兼容层。应确保托盘图标资源与主程序图标一致，并在应用退出时释放 NotifyIcon，否则 Windows 可能暂时保留“幽灵图标”。

### 14.2 开机自启动

- 安装器可选在 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 写入当前用户启动项。
- 设置页可在不需要管理员权限的情况下启用或关闭。
- 兼容早期“启动文件夹快捷方式”，切换方案时会清理旧入口。

### 14.3 数字签名

当前安装包没有 Authenticode 数字签名，Windows SmartScreen 可能显示“未知发布者”。这不是编译错误。面向公开分发时应购买代码签名证书，在打包后对 EXE 执行 SHA-256 时间戳签名。

## 15. PowerShell 脚本编码与执行策略

### 15.1 中文乱码导致解析失败

#### 现象

PowerShell 报告“表达式或语句中包含意外的标记”、“字符串缺少终止符”和“缺少右大括号”，同时中文变成类似 `姝ï満...` 的乱码。

#### 原因

Windows PowerShell 5.1 对“无 BOM 的 UTF-8”判断不一致，可能按本地 ANSI 代码页解码。如果乱码结果碰巧破坏引号，后续大括号也会被误报。

#### 解决方案

- 打包和模型下载 PowerShell 脚本的控制台文本改用 ASCII/English，避免依赖解码推断。
- 如果后续必须保留中文 PowerShell 字符串，文件应明确保存为 UTF-8 with BOM，并同时测试 PowerShell 5.1 和 PowerShell 7。

### 15.2 “此系统上禁止运行脚本”

#### 原因

Windows PowerShell Execution Policy 可被系统、企业组策略或当前用户设置为 `Restricted` / `AllSigned`，直接执行 `.\Package.ps1` 会被拒绝。

#### 解决方案

项目提供 `scripts\Package.cmd`：

```bat
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%~dp0Package.ps1" %*
```

该方式只对当前 PowerShell 子进程生效，不会永久修改系统执行策略。推荐打包命令：

```powershell
.\scripts\Package.cmd -Version 0.3.0
```

### 15.3 旧 PowerShell 没有 `Get-FileHash`

部分裁剪或旧环境中 `Get-FileHash` 不可用。模型下载脚本改为直接使用 .NET `System.Security.Cryptography.SHA256`，减少对 PowerShell 命令版本的依赖。

## 16. .NET SDK、NuGet 和中文路径

### 16.1 只安装 Runtime，没有 SDK

`dotnet` 命令存在不代表可以编译。如果 `dotnet --list-sdks` 无输出，说明只安装了 Runtime。项目打包脚本优先使用仓库 `.dotnet\dotnet.exe`，避免全局 PATH 中的 Runtime 抢在 SDK 前面。

### 16.2 NuGet 配置和缓存权限

受限环境可能无法读写 `%APPDATA%\NuGet` 或用户全局 `.nuget` 目录。因此 Build/Package 脚本会把以下路径重定向到仓库内的可控目录：

- `DOTNET_CLI_HOME`
- `NUGET_PACKAGES`
- `APPDATA`
- `NuGet.Config`

这也能减少不同开发机的全局 NuGet 配置对构建结果的影响。

### 16.3 中文、空格和长路径

项目路径包含中文用户名，安装后路径也可能包含空格。脚本必须：

- 使用 `Join-Path` 而不是手工拼接。
- 执行文件时使用 PowerShell `&` 和完整引号。
- 文件操作使用 `-LiteralPath`，避免方括号等字符被当作通配符。
- CMD 包装器使用 `%~dp0` 定位脚本自身目录。

## 17. 安装包体积

### 17.1 为什么 0.3.0 变大

0.3.0 安装包约 281.4 MB，主要原因不是 WPF 界面代码，而是：

- 自包含 .NET Windows Desktop Runtime。
- OCR Worker 及 OpenCV / ONNX Runtime 原生依赖。
- 中英日、English、Korean Mobile 模型。
- PP-OCRv5 Server det/rec 模型。

自包含的优点是目标电脑无需另外安装 .NET 10；缺点是安装包更大。

后续可选方案：

1. 快速版安装包只包含 Mobile 模型。
2. Server 模型作为 Inno Setup 可选组件。
3. 首次切换准确模式时下载，显示进度、支持断点续传并校验 SHA-256。
4. 在明确接受用户需要预装 .NET 的前提下，另外提供 framework-dependent 轻量包。

## 18. 设置持久化和升级兼容

### 18.1 难点

设置结构从单一翻译接口逐步升级为多实例列表，后续又增加快捷键、OCR 语言、旋转检测和精度模式。如果直接替换 JSON 结构，旧版用户升级后可能无法启动或丢失设置。

### 18.2 解决方案

- 存储对象的新字段放在可选参数中并提供默认值。
- 如果没有新的接口实例数组，从旧的单接口字段迁移。
- 快捷键键值为 0 时恢复应用默认值。
- OCR 精度未知或缺失时回退为 `fast`。
- API Key、代理密码使用 Windows DPAPI `CurrentUser` 保护。
- 写入时先生成临时文件，再覆盖目标文件，降低进程中断导致 JSON 损坏的风险。

## 19. 错误处理原则

本项目建议继续遵循以下原则：

- 截图、OCR、翻译、剪贴板分别报错，不要将所有失败统一显示为“截图失败”。
- 网络翻译失败不影响本地 OCR 原文。
- 重新识别失败不丢弃上一次成功结果。
- 后台控件识别失败时回退到窗口边界。
- 某一翻译接口失败时切换下一个，并显示实际成功的接口。
- 不对取消操作显示错误弹窗。
- 内部错误写日志，用户界面显示简短、可操作的信息。

## 20. 排查清单

### 20.1 无法截图

1. 查看日志中失败阶段是读取屏幕、创建遮罩还是 OCR 启动。
2. 检查是否仅在 DRM/游戏/远程桌面中出现。
3. 确认 Windows 显示缩放和多显示器排列。
4. 检查 GDI 句柄和 `BitBlt` 错误。

### 20.2 OCR 启动失败

1. 确认 `ocr\SnipTranslate.OcrWorker.exe` 存在。
2. 确认 `ocr\models` 中 det/cls/rec/字典成对存在。
3. 运行 Worker `--health`。
4. 使用模型下载脚本重新校验 SHA-256。
5. 检查 x64 架构、ONNX Runtime 和 OpenCV 原生 DLL。

### 20.3 英文识别不准

1. 点击“重新识别”或按 `Ctrl+R`。
2. 将源语言改为 `English`。
3. 在设置中切换为 Server 准确模式。
4. 尽量只框选文字区域，避免大面积无关背景。
5. 如果细字仍丢失，检查 det 阈值和放大后图像。

### 20.4 翻译失败

1. 在设置页选中某个接口并点击“测试翻译”。
2. 检查代理模式、地址、端口和证书。
3. 429 时等待冷却或调整接口顺序。
4. 401/403 时检查 API Key、Region 和请求头。
5. 自定义 API 检查 JSON 模板和响应路径。

### 20.5 无法打包

1. 优先运行 `.\scripts\Package.cmd -Version x.y.z`。
2. 确认 `.dotnet\dotnet.exe --list-sdks` 可看到 .NET 10 SDK，或系统 SDK 已加入 PATH。
3. 确认 Inno Setup 6/7 已安装且 `ISCC.exe` 可被找到。
4. 检查模型 SHA-256 失败是否由下载中断或代理替换内容导致。
5. 确认磁盘有足够空间容纳发布目录、Server 模型和最终安装包。

## 21. 后续优先级建议

### P0：可靠性

- 为 OCR 协议增加显式版本号，避免新主程序误连旧 Worker。
- 为翻译接口增加可配置超时、最大并发数和冷却状态可视化。
- 在安装/升级时检测已运行的旧版本，先正常退出再替换文件。

### P1：便捷性

- Server 模型按需下载，默认安装包保持轻量。
- 提供 OCR 候选结果切换，而不是只保留自动评分最高的一个。
- 为“重新识别”增加小菜单：标准、英文增强、Server 准确、旋转识别。

### P2：可维护性

- 建立固定 OCR 回归图集，包含小字、深色模式、多栏、旋转、高 DPI、中英混排和低对比度。
- 对文本布局重排、翻译熔断和设置迁移增加单元测试。
- CI 中同时运行编译、模型清单校验、PowerShell 5.1 语法检查和安装包无人值守安装/卸载测试。

## 22. 总结

SnipTranslate 的技术难点并不只是“截一张图再调 OCR”，而是要在 Windows 的 DPI、多屏、IME、剪贴板、全局快捷键、UI Automation、网络限流、原生 OCR 依赖和旧 PowerShell 环境之间保持连续、低打扰的交互。

当前方案的核心原则是：高频操作尽可能在同一个截图界面内完成；慢或不稳定的能力放到后台；任何附加功能失败都尽量不破坏已经取得的截图和 OCR 结果。
